# План: обязательные функции

Три функции закрывают условие задачи («3D-координаты движущегося **объекта (объектов)**… **восстанавливает его траекторию во времени**»)
и дают жюри цифры точности. Делаются параллельно, каждая — в своих файлах, через точки расширения.

| # | Функция | Модуль сервера | Интерфейс | Ветка |
|---|---|---|---|---|
| A | Отслеживание объектов (не только людей) | `peleng/ext/objects.py` (+ `peleng/objects.py`) | `web/ext/objects.js` | `feat/objects` |
| B | Восстановление траектории после записи + экспорт CSV/JSON | `peleng/ext/trajectory.py` (+ `peleng/trajectory.py`) | `web/ext/trajectory.js` | `feat/trajectory` |
| C | Точность: неопределённость точек, проверка по доске и рулетке, отчёт | `peleng/ext/accuracy.py` (+ `peleng/accuracy.py`) | `web/ext/accuracy.js` | `feat/accuracy` |

## Общие правила (для всех)

* **Точки расширения** — использовать их, а не править общие файлы:
  * сервер: `peleng/ext/<имя>.py` с `register(app, ctx)` (см. `peleng/ext/__init__.py`): REST под `/api/<имя>/…`,
    `ctx.pipeline.frame_hooks` (дополнить сообщение `frame`, см. `FrameContext` в `pipeline.py`),
    `ctx.pipeline.reset_hooks`, `ctx.pipeline.full_res([cam])` (кадры в полном разрешении), `ctx.hub.publish(msg)`;
  * настройки — `ctx.cfg.get("<имя>", {})`, значения по умолчанию внутри своего модуля;
  * вьювер: `web/ext/<имя>.js` (ES-модуль): `peleng.on(type, fn)`, `peleng.addSection(title)`, `peleng.THREE`, `peleng.scene`, …
* Общие файлы (`pipeline.py`, `server.py`, `reconstruct.py`, `tracking.py`, `geometry.py`, `index.html`, `config.py`) править **только если без этого никак**,
  маленькими точечными правками, и перечислить их в отчёте.
* Тесты — свой файл `backend/tests/test_<имя>.py`, на синтетике (`peleng/demo.py`, `make_cam` как в `tests/test_core.py`), без камер и без скачивания моделей.
  Все тесты (`python -m pytest -q tests` из `backend/`) должны проходить.
* Документация — свой файл `docs/<имя>.md` (что умеет, как пользоваться, формат данных); в `docs/data-format.md` — только ссылка/короткий раздел про новые поля.
* Стиль — как в проекте: комментарии и сообщения по-русски, без лишних абстракций.
* Python в `backend/.venv` (3.14). Новые зависимости — только если без них никак; тогда в `requirements.txt`.

## Общий формат данных

В сообщении `frame` (WebSocket `/ws/stream`, и он же строка в записи сессии `.jsonl`):

```jsonc
"persons": [ ... ],          // как сейчас (docs/data-format.md)
"objects": [                 // A: отслеживаемые объекты; поля как у persons, плюс kind/cls
  { "id": 101, "kind": "object", "cls": "sports ball" /* или "tag:7" для ArUco-метки */,
    "pos": [x,y,z], "vel": [vx,vy,vz], "speed": 0.4, "mode": "tri | mono",
    "cams": ["redmi","iphone15"], "reproj_err_px": 1.2, "predicted": false }
],
// C: у каждого элемента persons и objects (если есть 3D по ≥2 камерам):
//   "pos_std_m": [sx, sy, sz]  — оценка ошибки положения (1σ) из геометрии камер
```

ID объектов и людей не пересекаются (общий счётчик `Track._ids`). B читает и `persons`, и `objects` (если есть) — ключ трека `(kind, id)`,
где `kind` = `"person"` для persons.

## A. Отслеживание объектов

**Зачем:** в задаче «объект(ы)». Жюри может принести мяч, машинку, дрон.

**Режимы** (`cfg["objects"]["mode"]`, переключение из интерфейса без перезапуска):
1. `yolo` — обычная YOLO-детекция (`yolo11n.pt`, 80 классов COCO), фильтр по классам (`classes`, по умолчанию все, кроме `person`).
   Точка объекта — центр рамки. Модель грузится в фоне, как pose в `server.py`.
2. `aruco` — ArUco-метки, наклеенные на объект (словарь **не** `DICT_4X4_50`, который занят доской, — например `DICT_5X5_100`).
   Сопоставление между камерами — по ID метки. Самый точный режим, хорош для демо и проверки точности.
3. `off` — по умолчанию (чтобы не тратить CPU, пока не нужно).

**Конвейер:** хук в `frame_hooks` → детекция на `ctx.batch` (кадры уже в памяти) → сопоставление между камерами
(для yolo — класс + эпиполярное расстояние центров, венгерский алгоритм; функции из `geometry.py`) →
триангуляция (`triangulate_robust`) → свой `Tracker` (из `tracking.py`, отдельный экземпляр) → `msg["objects"]`.
Одна камера: точка на полу по низу рамки (объект на полу) — `mode: "mono"`.

**Интерфейс:** блок «Объекты»: режим, классы, счётчик; в 3D — сфера/куб цвета ID с подписью класса и след траектории.

**Скрипт:** `scripts/make_tags.py` — PDF с метками для печати (как `make_board.py`).

**Готово, когда:** тест на синтетике (точка, движущаяся по известной траектории, проецируется в 3 камеры → ошибка 3D < 2 см);
тест сопоставления двух объектов одного класса; режим `aruco` проверен на сгенерированном изображении метки; сервер в `--demo` не ломается.

## B. Восстановление траектории + экспорт

**Зачем:** «восстанавливает его траекторию во времени». Живой Калман — только сглаживание вперёд; после записи можно лучше.

**Модуль `peleng/trajectory.py`:**
* загрузка сессии `.jsonl` → треки `(kind, id)` → ряды `t, pos, mode, predicted, reproj_err_px`;
* **сшивка обрывков:** трек закончился, другой того же kind начался через ≤ `max_gap_s` в месте, согласном со скоростью, → один трек;
* **сглаживание вперёд-назад** (Калман + RTS-сглаживатель, постоянная скорость) с весами по `mode` (tri точнее mono), `predicted`-точки — не измерения;
* **заполнение пропусков** ≤ `max_gap_s` тем же сглаживателем, равномерная сетка (по умолчанию 30 Гц), у точки флаг `source: measured | interpolated` и σ;
* **метрики трека:** длительность, пройденный путь (по сглаженной траектории), средняя/максимальная скорость, число и длина заполненных пропусков.

**Экспорт:** CSV (`t, kind, id, x, y, z, vx, vy, vz, speed, source, std`) и JSON; для сырых и восстановленных данных.

**API:** список сессий (`data/sessions/*.jsonl`), восстановление сессии, скачивание CSV/JSON, скрипт `scripts/restore_session.py` для командной строки.

**Интерфейс:** блок «Траектории»: выбор записанной сессии → «Восстановить» → гладкие линии в 3D поверх сырых, таблица метрик, кнопки скачать CSV/JSON.

**Готово, когда:** тесты: зашумлённая синтетическая траектория с пропусками → ошибка восстановленной заметно меньше сырой, пропуск 0.5 с заполнен с ошибкой < 10 см;
сшивка двух обрывков одного человека и **не**сшивка двух разных людей; экспорт CSV читается обратно.

## C. Точность

**Зачем:** жюри верит цифрам. Нужны и автоматические оценки, и проверка по рулетке.

**1. Неопределённость точки** (`pos_std_m`): по положению точки и камерам, которые её видели, — ковариация триангуляции
при шуме измерения σ пикселей (по умолчанию 2 px; якобиан проекций). Хук с `ORDER` больше, чем у objects, — чтобы дополнить и `objects`.
Во вьювере — кольцо/эллипс вокруг человека, размер = σ.

**2. Проверка по доске** (автоматическая, без рулетки): доска видна ≥ 2 камерам → её углы триангулируются по нескольким камерам
(не через калибровку положения!) → расстояния между углами сравниваются с известным размером клетки → ошибка в мм, плюс отклонение плоскости.
Доску можно положить в другое место комнаты, не туда, где калибровали, — так проверяется точность по всей зоне.

**3. Проверка по рулетке:** «Точка A» (усреднение положения человека/объекта за ~1 с) → перейти → «Точка B» → ввести измеренное рулеткой расстояние →
ошибка в см и %. История проверок сохраняется (`data/accuracy.json`).

**4. Отчёт:** по камерам — ошибка калибровки (px), углы между лучами камер в центре зоны (< 20° — предупреждение «камеры почти на одной линии»),
итоговая сводка проверок. JSON + блок в интерфейсе.

**Готово, когда:** тесты: σ уменьшается при добавлении камеры и растёт при сужении угла между камерами; проверка по доске на идеальных синтетических камерах
даёт ошибку ≈ 0, с шумом — ожидаемую; расчёт A→B на синтетике.
