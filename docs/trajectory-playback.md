# Воспроизведение траекторий на фронтенде

Главная страница открывает **Траектории**. Режим **Live-камеры** сохранён
и доступен также по `/?workspace=live`.
Вычисление координат, детекция и оценка точности остаются задачей бэкенда.
Project 02 показывает исходные координаты из материалов, а не результат детекции.

## Запуск

```bash
cd frontend
npm ci
npm run dev
```

Откройте напечатанный Vite адрес с `/static/build/`.
Демонстрация работает без Python-сервера. Для live-режима нужен сервер проекта
на `https://localhost:8443`: Vite проксирует API, WebSocket и legacy-ресурсы.
Production: `npm run build`, затем обычный запуск бэкенда из основной инструкции.
Проверка математики и исходного набора: `npm test`.

## Материалы Project 02

`project2.zip.001`–`.004` — части **одного** ZIP. Внутри пять MP4,
пять CSV трансформаций камер и CSV движения объекта, **не SVG**.
CSV и предоставленная модель `CargoTruck.fbx` включены в frontend.
Крупные MP4 намеренно исключены из git. В текущем рабочем каталоге они распакованы.
На другой машине можно загрузить их кнопкой **Видео** либо подготовить демо:

```bash
cat /путь/project2.zip.001 /путь/project2.zip.002 /путь/project2.zip.003 /путь/project2.zip.004 > /tmp/peleng-project2.zip
unzip /tmp/peleng-project2.zip -d frontend/public/demo
# Затем npm --prefix frontend run build, если используется production.
```

Не переименовывайте `project2/Way1.FinalImage.CineCameraActor1.mp4`–`5.mp4`,
если хотите автоматическое подключение демо-видео.
Сборка копирует видео в `backend/web/build/demo/project2/`.
Для импортируемых видео начало клипа должно соответствовать времени **0 секунд**.
Оригинальные клипы содержат 1001 кадр при 30 кадр/с; CSV — кадры 0–1001.
Последний отсчёт CSV на один кадр позже конца видео; клип останавливается
на последнем доступном изображении.

В демо приняты сантиметры Unreal, Z вверх, 30 кадр/с. Во внутреннем
представлении — метры, абсолютные XYZ, секунды. Перед импортом другого
CSV можно задать его единицы и частоту. Высота Z не прижимается к полу.
Центр FBX следует XYZ; исходные размеры FBX переводятся из сантиметров
в метры (длина около 6.68 м). Это визуализация, не доказательство того,
что точка трекинга бэкенда совпадает с геометрическим центром модели.
Камеры показаны по исходным позициям и углам; их пирамиды — иллюстрация
по фокусному расстоянию и сенсору 23.76 × 13.365 мм, не новая калибровка.

**Дефект оригинала:** в строках с кадрами 402 и 691 координаты записаны
как текст (`авг.13`, `июл.25`, исходная кодировка Windows-1251).
Демо теперь читает проверенные **производные копии** из `clean/`.
Все шесть файлов перекодированы в UTF-8. Все 1002 кадра сохранены.
В грузовике оценены ровно две повреждённые ячейки:
`Loc_X[402] = 8.80835 см`, `Loc_Y[691] = 7.87305 см` — линейная
интерполяция соседних значений. Это **оценки, не восстановленный ground truth**:
исходные числа из строк Excel однозначно определить нельзя.
Остальные ячейки не менялись, исходные файлы оставлены без изменений.
`clean/report.json` содержит исходный текст, соседние измерения, метод,
SHA-256 оригиналов и копий. Интерфейс позволяет скачать CSV и отчёт.
Обычный импорт повреждённых файлов по-прежнему отклоняется с номером строки.

Пересоздать и проверить копии:

```bash
npm --prefix frontend run prepare:demo
npm --prefix frontend test
```

Автовосстановление разрешено только для одиночной координаты между
двумя числовыми значениями в последовательных кадрах. Несколько пропусков
подряд, повреждённые время/вращения и крайние строки отклоняются.

Все пять исходных MP4 проверены полным декодированием: по 1001 кадру,
1920×1080, 30 кадр/с, без ошибок декодирования в установленном OpenCV.

## Дрон: фактический 2D-трекинг в камере 5

Дрон с пользовательского скриншота найден в `CineCameraActor5`, кадр 210
(7 секунд), ROI **x=1292, y=185, w=86, h=55** в исходных 1920×1080.
Эта начальная рамка задана вручную, а не найдена нейросетью.

Реализован [OpenCV Template Matching](https://docs.opencv.org/4.x/d4/dc6/tutorial_py_template_matching.html):
локальный поиск исходного шаблона на пяти масштабах, нормализованная
корреляция `TM_CCOEFF_NORMED`, порог 0.65 и отрыв от второго пика 0.04.
Шаблон не подменяется каждым новым кадром, чтобы не накапливать дрейф.
После неудачного совпадения bbox отсутствует; после 30 пропусков требуется
новая инициализация. Большие повороты, перекрытия и появление заново в другой
части кадра этим базовым методом **не решены**.

Результат `drone-camera5.json` вычислен по всем 1001 кадрам, без CSV грузовика.
В 625 кадрах есть совпадение, в 376 — явный пропуск. Это **не метрика
точности**: нет размеченной контрольной последовательности. Визуально
проверены кропы раз в секунду: до ~20 с рамка на дроне; при повороте камеры
совпадение теряется, рамка исчезает, а не переносится на грузовик.
В этом прогоне p95 обработки одного кадра ~6.36 мс без учёта декодирования/seek.
JSON сохраняет исходный SHA-256 видео и время обработки каждого кадра.

Повторить из корня проекта (используйте Python из окружения backend):

```bash
backend/.venv/bin/python backend/scripts/track_video.py \
  frontend/public/demo/project2/Way1.FinalImage.CineCameraActor5.mp4 \
  --seed-frame 210 --roi 1292 185 86 55 \
  --camera-id cam-5 --object-id drone-1 --label drone \
  --output frontend/public/demo/project2/drone-camera5.json
```

Для другого объекта/видео задайте его ROI, кадр, ID и label.
Экспорт JSON атомарный, исходное видео не перезаписывается.
Исходник видео нужен только для пересчёта; готовый трек сохранён в git.
В интерфейсе выберите **CAM 05 · 2D**, при необходимости разверните видео.
Рамка привязана к фактическому времени video-элемента, а не скорости 3D-сцены;
при перемотке и потере совпадения старый bbox не сохраняется.
Для загруженных вручную других видео этот трек не используется.

### Что передать участнику бэкенда

- Обычная COCO-модель в `YoloObjectDetector` не имеет класса `drone`.
  Для автоматического обнаружения нужен детектор с обученным классом дрона
  и проверкой на данном синтетическом домене, затем ByteTrack/BoT-SORT
  для сопровождения детекций. Трекер не создаёт отсутствующий класс.
- Если разрешена начальная ручная рамка, текущий OpenCV-метод уже воспроизводим.
  Альтернатива — [CSRT](https://docs.opencv.org/4.x/d2/da2/classcv_1_1TrackerCSRT.html),
  но в установленном OpenCV 5.0.0 `TrackerCSRT_create` отсутствует;
  заменять основной пакет на contrib без проверки всего окружения не стали.
- `frames[].bbox` — `[x, y, width, height]` в исходных пикселях,
  `time` — секунды, `camera_id` — камера. Центр bbox может служить
  **приближённой** 2D-точкой, но одинаковая физическая точка на разных ракурсах
  не гарантирована.
- Для XYZ нужны синхронные наблюдения этого же дрона минимум с двух
  калиброванных камер, согласованные ID и проверка репроекции. В демо
  подтверждён только 2D-трек камеры 5, поэтому дрону не присвоены выдуманные XYZ.
- Существующий `objects.py` ориентирован на наземные объекты:
  `mono_object` проецирует YOLO bbox на пол, а `reconstruct_objects` ограничивает
  триангуляцию по высоте `-1 < Z < 5`. Для летающего дрона такие допущения
  нужно отдельно пересмотреть; новый скрипт не вмешивается в этот пайплайн.

## Контракт CSV

Один объект на файл; можно выбрать несколько файлов одновременно.
Заголовок обязателен, разделитель `;` или `,`.

```csv
Frame;Loc_X;Loc_Y;Loc_Z
0;0;0;300
1;10;20;301
2;20;40;302
```

Время равно `Frame / fps`. Номера кадров должны строго возрастать,
числа должны быть конечными, пустые значения не разрешены.
CSV с `Rot_Yaw` распознаётся как файл камеры и не принимается вместо объекта.
Для нескольких объектов используйте общую временную шкалу, не сдвигайте каждый
объект к собственному нулю.

## Предлагаемый контракт SVG для бэкенда

В переданном наборе нет SVG, поэтому поддержку произвольного формата
бэкенда нельзя подтвердить. Ниже — **явный поддерживаемый контракт**.
Если бэкенд экспортирует другой шаблон, нужен пример для отдельного адаптера.
График matplotlib с осями и подписями сам по себе не является 3D-траекторией:
из него нельзя надёжно восстановить XYZ и время.

```xml
<svg xmlns="http://www.w3.org/2000/svg" data-units="m">
  <polyline
    data-track-id="truck-1"
    data-name="Грузовик 01"
    points="0,0 1,0.2 2,0.5"
    data-times="0 0.1 0.2"
    data-z="3 3.01 3.02"
  />
  <polyline
    data-track-id="truck-2"
    points="10,5 9,5 8,5"
    data-times="0 0.1 0.2"
    data-z="3 3 3"
  />
</svg>
```

- `data-units` на корневом `svg`: `m`, `cm`, `mm`.
- Каждый `polyline[data-track-id]` — отдельный объект, ID уникальны.
- `points` содержит **мировые X,Y**, не пиксели изображения и не экранные Y вниз.
- `data-times` — абсолютное время в секундах, строго возрастающее.
- `data-z` — мировая высота на каждую точку, в единицах `data-units`.
- Число пар XY, времён и Z должно совпадать, не меньше двух.
- `viewBox`, цвет и оформление не влияют на координаты.
- `transform` не поддерживается: экспортируйте уже преобразованные координаты.
- SVG разбирается как данные через `DOMParser`, не вставляется в DOM и
  не исполняется. Скрипты/стили/внешние изображения из SVG не используются.

В **Параметры импорта и URL бэкенда** можно указать URL CSV или SVG
(например, `/api/trajectories/export.svg`) и нажать **Получить с бэкенда**.
Такого endpoint сейчас не добавлено: его реализует участник бэкенда.
HTTP-ошибки и ошибки формата отображаются, ранее загруженная сцена сохраняется.
Для другого origin нужен CORS; получение данных — явная загрузка снимка,
не подписка на live-поток. Обновлённый файл можно запросить повторно.

Ограничения: 32 объекта, 200 000 отсчётов на объект,
500 000 отсчётов на всю сцену, файл до 32 МБ.
Поддерживаются только грузовики с общей FBX-моделью.

## Воспроизведение и производительность

- Один цикл рендера Three.js; движение зависит от прошедшего времени,
  а не от частоты кадров дисплея.
- На паузе GPU перерисовывает сцену только при изменениях (камера, размер,
  перемотка, видимость), а не непрерывно.
- Между отсчётами — линейная интерполяция без сплайнов, меняющих форму пути.
  Поворот визуальной модели сглаживается по кратчайшему углу, XYZ не изменяются.
- При разрыве больше 0.5 с объект скрывается до следующего измерения;
  линия не соединяет такой разрыв. Длинные пропуски не экстраполируются.
- Доступны пауза, перемотка, шаг 1/fps, скорости 0.25×–2×, повтор,
  выбор объекта, следование камеры и обзор всей траектории.
- Исходные данные хранятся в typed arrays, поиск отсчёта — бинарный.
  Буферы линий строятся при загрузке, затем меняется draw range.
- Части FBX объединяются по материалу один раз при загрузке. Клоны
  грузовиков используют общие геометрии и материалы.
- React-телеметрия обновляется не чаще 10 раз/с, не в каждом 3D-кадре.
  Графики ограничены примерно 400 точками на ось.
- Pixel ratio ограничен 1.5, нет постобработки и динамических теней.
  Модель и Three.js загружаются отдельно от live-интерфейса.
- Декодируется одно выбранное видео; остальные не создают video-элементов.
  Видео корректируется при рассинхронизации больше 150 мс, на паузе
  точность позиционирования — 15 мс (точность самого seek зависит от браузера).
- Рендер и видео приостанавливаются в скрытой вкладке/неактивном режиме;
  при переключении источник времени не скачет вперёд.
- ResizeObserver, обработчики, WebGL-ресурсы и object URL освобождаются.
- В сцене показаны измеренные FPS и p95 интервала кадров; внизу панели —
  draw calls и число треугольников. Это диагностика текущего устройства,
  не обещание фиксированных 60 FPS на любом оборудовании.
