# Траектории: восстановление после записи и экспорт

Живой фильтр Калмана (`peleng/tracking.py`) сглаживает только «вперёд» — по прошлому. После записи сессии доступна
вся запись целиком, поэтому траекторию можно восстановить точнее: каждая точка оценивается и по прошлому, и по будущему,
обрывки одного человека склеиваются, короткие пропуски заполняются.

Код: `backend/peleng/trajectory.py` (алгоритм), `backend/peleng/ext/trajectory.py` (REST), `backend/web/ext/trajectory.js` (блок во вьювере),
`backend/scripts/restore_session.py` (командная строка), тесты — `backend/tests/test_trajectory.py`.

## Что делает

1. **Загрузка записи** `data/sessions/*.jsonl` (первая строка `hello`, дальше `frame`). Треки собираются по ключу `(kind, id)`:
   `persons` → `kind = "person"`, `objects` (если есть) → `kind` из записи (`"object"`), класс `cls` сохраняется.
   У каждой точки — `t, pos, mode, predicted, reproj_err_px` (и `vel`, `pos_std_m`, если есть). Оборванная последняя строка
   (запись ещё идёт) пропускается.
2. **Сшивка обрывков.** Трек A кончился, трек B того же `kind` (и того же `cls`) начался через `0 ≤ пропуск ≤ max_gap_s`,
   и начало B лежит рядом с продолжением A по его скорости (скорость — прямая по последним 0.5 с измерений A):
   `|p_B − (p_A + v_A·пропуск)|_xy ≤ stitch_gate_m + stitch_slack_mps·пропуск` → один трек (ID — первого обрывка,
   все ID записи — в `merged_ids`). Треки, которые видны одновременно, не сшиваются. Пары выбираются жадно, начиная с самых близких.
   Конец трека — последнее **измерение**: хвост прогноза живого трекера не мешает сшивке.
3. **Сглаживание вперёд-назад**: фильтр Калмана с моделью постоянной скорости (по осям независимо, шум ускорения `accel_std`)
   + сглаживатель Рауха–Тунга–Штрибеля (RTS). Вес точки — по `mode`: σ tri = 5 см, mono = 20 см по горизонтали / 30 см по высоте
   (как у живого трекера); у tri σ растёт при ошибке репроекции больше `reproj_ref_px` (до ×4); если в записи есть `pos_std_m`
   (функция «Точность»), σ не меньше него. Точки с `predicted: true` — **не измерения**, в сглаживание не идут.
4. **Равномерная сетка** `rate_hz` (по умолчанию 30 Гц, время кратно 1/rate_hz). Пропуски между измерениями ≤ `max_gap_s`
   заполняются тем же сглаживателем — у таких точек `source = "interpolated"`, у остальных `"measured"`.
   Пропуском считается интервал между измерениями длиннее `max(2.5 × обычный шаг, 2 / rate_hz)`.
   Пропуски длиннее `max_gap_s` не заполняются: трек на них рвётся (на сетке там нет точек).
   У каждой точки `std` — σ положения из ковариации сглаживателя (среднеквадратичная по осям, м); в пропусках она больше.
5. **Метрики трека**: длительность (без незаполненных разрывов), пройденный путь по сглаженной траектории,
   средняя (путь / длительность) и максимальная скорость, число и суммарная длина заполненных пропусков, разрывы,
   число измерений/прогнозов, путь по сырым точкам (для сравнения — шум его завышает), доля tri, средняя σ.
   У людей путь и скорость — **горизонтальные** (как `speed` в `frame`), у объектов — полные 3D.

Оговорка: в записи лежат позиции, уже сглаженные живым фильтром (сырых наблюдений там нет). Восстановление
работает с ними как с измерениями; на синтетике с шумом 5 см ошибка падает в ~3 раза (см. тесты).

## Как пользоваться

**Во вьювере**: «● Записать сессию» → походить → «■ Остановить запись». В блоке **«Траектории»** выбрать запись
(список обновляется сам, кнопка ⟳ — сразу), при желании поменять «пропуск ≤ … с» и «сетка … Гц» → **«Восстановить»**.
В 3D появятся гладкие линии цвета ID (белые участки — заполненные пропуски) поверх бледных сырых точек
(галочка «показывать сырые точки»), таблица метрик по трекам (наведение на строку — подробности) и ссылки
«скачать CSV/JSON» для восстановленных и сырых данных. «Скрыть» убирает линии.

**Из командной строки** (из `backend/`):
```
python scripts/restore_session.py ../data/sessions/session_20261103_120000.jsonl
python scripts/restore_session.py запись.jsonl --max-gap 1.0 --rate 60 --out результаты/ --raw
```
Пишет `<имя>_restored.csv/.json` (с `--raw` — ещё `<имя>_raw.csv/.json`) рядом с записью или в `--out` и печатает таблицу метрик.

**Из Python**:
```python
from peleng import trajectory as tj
res = tj.restore_session("session.jsonl", max_gap_s=1.0)
for r in res.restored: print(r.kind, r.id, r.merged_ids, r.metrics)
open("out.csv", "w").write(tj.to_csv(res))
```

## Параметры (`config.json` → `"trajectory"`)

| Параметр | По умолчанию | Что значит |
|---|---|---|
| `max_gap_s` | 1.5 | макс. пропуск для сшивки и заполнения, с (как `max_age_s` живого трекера) |
| `rate_hz` | 30 | частота выходной сетки, Гц |
| `accel_std` | 1.5 | шум ускорения модели, м/с²: меньше — глаже, но хуже резкие повороты |
| `meas_std` | `{"tri": [0.05, 0.05], "mono": [0.2, 0.3]}` | σ измерения [xy, z], м |
| `reproj_ref_px` | 8 | с какой ошибки репроекции tri-точка теряет вес |
| `stitch_gate_m` | 0.5 | допуск по месту при сшивке, м … |
| `stitch_slack_mps` | 1.0 | … плюс столько метров на секунду пропуска |
| `min_points` | 3 | треки с меньшим числом измерений не восстанавливаются |

`max_gap_s` и `rate_hz` можно передать и в запросе/интерфейсе/скрипте.

## REST

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/trajectory/sessions` | записи: `[{"name", "size", "mtime", "recording"}]`, новые сверху |
| GET | `/api/trajectory/restore?session=<имя>&max_gap_s=&rate_hz=` | сводка: `params`, `raw_tracks`, `tracks`, `t0`, `t1`, `items` (метрики по трекам), `restored`/`raw` — линии для 3D (не больше 3000 точек на трек) |
| GET | `/api/trajectory/export?session=<имя>&fmt=csv\|json&data=restored\|raw&max_gap_s=&rate_hz=` | скачать файл `<имя>_<data>.<fmt>` |

`session` — только имя файла из `data/sessions` (`*.jsonl`, без путей). Расчёт идёт в отдельном потоке, результат кэшируется
(последние 4 комбинации сессия+параметры; при изменении файла пересчитывается).

## Формат экспорта

**CSV** (UTF-8, разделитель `,`, первая строка — заголовок):
```
t,kind,id,x,y,z,vx,vy,vz,speed,source,std
1793655154.7000,person,1,1.5036,0.0813,0.9514,-0.1167,0.4386,-0.0027,0.4539,measured,0.0249
```
* `t` — время, с (часы сервера, как `t` в `frame`); `x, y, z` — м (мир: Z вверх, пол z = 0); `vx, vy, vz`, `speed` — м/с;
* восстановленные: `source` = `measured | interpolated`, `std` — σ положения, м; строки по трекам, внутри — по времени;
* сырые: строки как в записи (ID записи, без сшивки), по времени; `source` = `tri | mono | predicted`;
  `vx…speed` — из записи; `std` — из `pos_std_m` (пусто, если его нет).

**JSON**:
```jsonc
{ "format": "peleng-trajectory/1", "data": "restored", "units": "m, s", "up": "z", "session": "session_….jsonl",
  "params": { "max_gap_s": 1.5, "rate_hz": 30.0, ... },
  "tracks": [ { "kind": "person", "id": 1, "merged_ids": [1, 7], "cls": null,
                "metrics": { "duration_s": 7.9, "path_m": 4.4, "speed_mean_mps": 0.56, "speed_max_mps": 0.68,
                             "gaps_filled": 1, "gaps_filled_s": 0.6, "gap_max_s": 0.6, "breaks": 0, "path_raw_m": 4.5, "std_mean_m": 0.017, ... },
                "t": [...], "pos": [[x,y,z], ...], "vel": [[vx,vy,vz], ...], "source": ["measured", ...], "std": [...] } ] }
```
Сырые (`"data": "raw"`): у трека `t, pos, vel, mode, predicted, reproj_err_px` (нет данных — `null`).
