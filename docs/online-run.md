# Запуск демо одной командой и онлайн-прогон

`run_online.ps1` / `run_online.sh` поднимают сервер и открывают страницу «Траектории» Project 02 (`http://localhost:8600/`).
Есть два режима.

* **Воспроизведение (по умолчанию).** Эталон и оценка нашей модели (`frontend/public/demo/project2/estimate/truck.csv`,
  пакетный прогон `offline/run.py`, пресет `truck_fused`, веса `models/truck_pose_All.pt`) проигрываются под видео.
  След рисуется **только позади грузовика**, по мере проигрывания. Весь маршрут наперёд можно включить кнопкой
  «Маршрут» справа от сцены.
* **Онлайн-расчёт — `http://localhost:8600/?online=1`.** Пять видео играют как живые камеры, сервер считает грузовик
  в момент показа. На CPU это около 1 точки в секунду, поэтому след идёт рывками; режим нужен на машине с GPU / M-чипом.

## Запуск одной командой

Нужны Python 3.11–3.13 (на 3.14 тоже работает, но с предупреждениями torch) и Node.js 18+, чтобы один раз собрать фронтенд.
Видео в git нет — нужна папка с `Way1.FinalImage.CineCameraActor1..5.mp4` и `object_transform_*.csv`.

Windows:
```bash
powershell -ExecutionPolicy Bypass -File run_online.ps1 -Data "C:\Programming\project2"
```

macOS / Linux:
```bash
./run_online.sh /путь/к/project2
```

Первый запуск сам создаёт `backend/.venv`, ставит `backend/requirements.txt` и собирает фронтенд.
Затем он докачивает `yolo11s.pt` (19 МБ) в `models/` и открывает `http://localhost:8600/`.
Онлайн-прогон стартует при открытии `/?online=1`. Кнопка «Перезапустить» в блоке «Онлайн-прогон» запускает его с начала видео.

Параметры:
* `-Port` / `--port` — порт сервера.
* `-Device` / `--device` — устройство: `auto` (CUDA → MPS → CPU), `cpu`, `cuda:0`, `mps`.
* `-Rebuild` / `REBUILD=1` — пересобрать фронтенд после `git pull`.

Те же опции принимает и сам сервер:
```bash
python offline/online.py --data <папка> [--weights models/truck_pose_All.pt] [--roi-weights yolo11s.pt] [--roi-below 99] [--fallback roi|none] [--no-browser]
```

## Что происходит

1. **Камеры.** У каждой камеры свой поток. Кадр k «снимается» в момент `t0 + k/30` по реальным часам.
   Кадры проматываются без распаковки (`grab`, аппаратное декодирование, если есть). В картинку
   распаковывается только кадр, который запросил рабочий цикл, как у живой камеры, у которой
   забирают свежий кадр.
2. **Шаг.** Рабочий цикл просит у всех камер следующий кадр по часам и выполняет три действия:
   * прогоняет **наш детектор позы грузовика** `models/truck_pose_All.pt` по всем камерам одним вызовом сети.
     Это YOLO-pose с 9 точками, обучена `offline/detectors/run_truck_train.ps1`, mAP50 позы 0.93;
   * если поза в какой-то камере молчит, а трек уже есть, ищет **YOLO в окне вокруг прогноза** трекера
     (`yolo11s.pt`, все окна одним вызовом);
   * делает шаг **3D-трекера** (`offline/tracker3d.py`, настройки пресета `truck_fused`): триангуляция по 2+ камерам,
     фильтр Калмана, гейтинг выбросов.
3. **Пропуск кадров.** Кадры, пришедшие, пока сеть занята, пропускаются, как в живой системе. Точка шага
   посчитана только по кадрам ≤ k. Трекер учитывает реальный шаг по времени между обработанными кадрами.
4. **Отправка.** Каждая точка сразу уходит по WebSocket `/ws/online`. Фронтенд дорисовывает след.
   Между точками модель грузовика едет по последней скорости. Контрольное видео справа показывает
   **последний обработанный кадр**, а не опережающее его видео по часам. Поэтому рамка относится
   именно к показанному изображению. После завершения прогон останавливается; позднее подключение
   открывает последний обработанный кадр.

## Рамки и надёжность

Блок **«Точность и вычисления»** скрыт из интерфейса. Сохранённый компонент накладывает две временные линии: золотая сплошная —
евклидова ошибка исходных XYZ относительно синхронного эталона (метры, левая шкала),
голубая пунктирная — частота результатов по последним 10 обработанным шагам
(Гц, правая шкала). Это независимые шкалы, не процент точности и не FPS рендера.
Ошибка использует исходные координаты, не визуальное сглаживание. До инициализации,
без XYZ или без синхронного эталона ошибка не отображается; пропуски не заменяются нулём.
История рисуется только до текущего времени воспроизведения. В готовой CSV-записи
есть только линия ошибки; частота вычислений и правая шкала скрыты — для них нужен онлайн-прогон.

В контрольном видео зелёная рамка — детекция, использованная при обновлении XYZ; жёлтая пунктирная —
кандидат, не использованный трекером. Процент рядом — уверенность детектора, **не точность XYZ**.
На другом кадре старая рамка не удерживается. У каждой камеры своё разрешение; кадры разных
номеров не объединяются в одно многокамерное измерение.

Блок источника различает многокамерное измерение, один ракурс, прогноз без наблюдений,
ограниченную коррекцию при восстановлении и отсутствие надёжных XYZ. Показанная σ — внутренняя
оценка фильтра, не измеренная ошибка относительно эталона.

Для готового воспроизведения вместе с `truck.csv` используется
`frontend/public/demo/project2/estimate/truck_observations.json`. Пакетный запуск автоматически
создаёт `<имя_объекта>_observations.json` рядом с CSV; оба файла нужно переносить из одного прогона.
JSON содержит `fps`, `cams`, разрешения `sizes` по камерам и последовательность `points`
с `frame`, `t`, `mode`, `n_cams`, `sigma_m`, `limited_update`, `used_det`, `dets`.
Поле `trajectory_sha256` связывает статусы надёжности и выбранные детекции с конкретным CSV
(UTF-8, переводы строк LF). При несовпадении или отсутствии хеша старые статусы скрываются;
рамки остаются обычными детекциями видео, без утверждения об использовании в новом XYZ.

Проверка полного онлайн-прогона на текущем Mac / MPS (5 камер, 1001 кадр, 33.37 с):
339 обработанных точек, около **10.2 обновления XYZ/с**; медиана задержки **71 мс**,
p95 **135 мс**, медиана вычислительного шага **61 мс**. Это частота обработанных точек,
не 30 FPS входного видео. Прогон дошёл до кадра 999 и завершился без ошибок браузера
и нечисловых координат. На 336 точках с XYZ: RMSE **4.39 м**, медиана **0.97 м**,
максимум **24.58 м**. Это один прогон на демонстрационных данных, не независимый тест:
при одном ракурсе глубина всё ещё может ошибаться значительно. Скорость и точность
зависят от устройства и того, какие кадры успел обработать сервер.

## Скорость и точность (ноутбук HP i7-10510U, CPU, 5 камер 1920×1080)

| Окно вокруг прогноза | Точек в секунду | Шаг | RMSE 3D | Медиана |
|---|---|---|---|---|
| `yolo11m.pt` | 0.5 | 2.2 с | 2.9 м | 0.7 м |
| **`yolo11s.pt` (по умолчанию)** | 0.85 | 1.1–1.2 с | 2.0–2.7 м | 0.9–1.0 м |
| `yolo11n.pt` | 1.2 | 0.8 с | 8.5 м | 0.8 м |
| `yolo11s.pt`, `--roi-below 2` | 1.4 | 0.5 с | 5.2 м | 0.7 м |

Ошибка считается против эталона по тем кадрам, где пришла точка.
Сама детекция позы на 5 камерах занимает около 0.33 с, остальное — окна и декодирование видео.
Разброс между прогонами заметен: кадры, на которые попадает обработка, зависят от времени.
На GPU (`--device cuda:0`) или Mac с M-чипом (`--device mps`) обработка обычно быстрее,
но это не гарантирует меньшую ошибку: она зависит также от ракурсов и пропущенных кадров.
Локальный проверенный прогон (`offline/run.py`, пресет `truck_fused`) дал RMSE 3.23 м.
Готовый CSV в интерфейсе обновлён из main (`313ad8f`, RMSE 1.648 м);
это не обновление локальных весов и не показатель текущего онлайн-прогона.

Поля точки WebSocket:
* `frame`, `t` (с от начала видео);
* `pos` (Unreal, см);
* `vel` (см/с);
* `mode` (`tri` / `mono` / `predict` / `init` / `none`);
* `limited_update` — коррекция EKF ограничена по допустимому перемещению;
* `n_cams`, `cams`;
* `sigma_m`;
* `proc_ms`, `detect_ms`;
* `lag_ms` — задержка от «съёмки» кадра до отправки;
* `dets` — рамки по камерам.
* `used_det` — пары `[индекс камеры, индекс детекции]`, участвовавшие в обновлении.

Первое сообщение `hello` несёт `t0`, `server_time`, `fps`, `cams`, `sizes`, `done`
и уже посчитанные `points`. Подключившийся позже зритель видит весь прогон.
